# API Integration Guide

For an external caller (e.g. a Java SaaS backend) integrating with the Brand
Intelligence Engine over HTTP. If you haven't read
[`architecture.md`](architecture.md) or
[ADR 0005](adr/0005-no-auth-layer.md), the two things to know going in:
this engine has **no auth layer** (it assumes it's only reachable from your
own trusted network) and **no synchronous "run a scan and get the answer in
the response" endpoint** — scans take minutes, so the API hands you a job id
and you check back.

---

## 1. Ground rules

| | |
|---|---|
| Base URL | wherever this engine is deployed, e.g. `http://brand-intel-engine:8000` |
| Content type | `application/json` for every request body and response |
| Auth | none — network-level trust only (see ADR 0005) |
| Errors | every non-2xx response is `{"detail": "human-readable message"}` |

Error status codes you'll actually see:

| Status | Meaning |
|---|---|
| `404` | the id in the URL doesn't exist (client, profile, job) |
| `422` | the request body/params failed validation (bad platform id, missing required field) |
| `409` | the request is well-formed but the current state won't allow it (e.g. cancelling a job that already finished) |
| `502` | the platform being scraped itself misbehaved (checkpoint, quota, flood-wait) — this is a job *failure*, not an API error; you'll see it inside a job's `error` field, not as an HTTP status on the call that started the job |

There is no request envelope, no correlation id, no pagination cursor —
just plain JSON in, plain JSON out. Full machine-readable schema (for
generating a Java client via `openapi-generator`) is served live at
`GET /openapi.json`; human-browsable docs at `GET /docs`.

---

## 2. The end-to-end flow

```
1. POST /clients                register the brand you want protected
2. POST /discovery               find candidate profiles          -> job_id
      ... poll GET /jobs/{job_id} until status = done ...
3. GET  /profiles?phase=discovery  review what was found (cards)
4. PATCH /profiles/{id}          approve or reject each candidate
      approving auto-queues analysis for that profile -- no separate call
      ... poll GET /jobs/{job_id} (kind=analysis) until done ...
5. GET  /profiles?phase=analysis   read the scored, scraped results
6. POST /profiles/{id}/publish   confirm a result -> writes the client-facing finding
```

Steps 3–4 (reviewing and approving candidates) are a real decision point —
this tool finds *candidate* impersonating profiles, it does not decide on
its own that a match is real. Either a human reviews them in the bundled
UI, or your platform makes that call programmatically via `PATCH
/profiles/{id}`. There's no way to skip straight from discovery to a
finished, scored result — analysis only ever runs on profiles that have
been explicitly approved.

Step 6 also matters: analysis produces a *scored* result, but nothing is
written to the client-facing findings store until you explicitly publish it
(or it auto-publishes after a hold window — see §5). If you don't call
`publish`, the result exists but is not a "finding" yet.

---

## 3. Main APIs — where the actual logic lives

These are the endpoints with real business logic behind them. Everything
in §7 is operational/admin surface you likely won't call from an
integration.

### 3.1 Register a client — `POST /clients`

Upsert. Must be called once before you can discover or analyse anything
for this client — `client_id` is **your own** id (org/customer id), passed
through unchanged, never generated by this engine.

**Request**
```json
{
  "client_id": "acme-corp",
  "name": "Acme Corp",
  "domain": "acme.com",
  "name_keywords": ["Jane Doe", "John Smith"],
  "domain_keywords": ["Acme", "Acme Corp", "AcmeOfficial"],
  "asset_name_individual_keywords": ["Jane Doe"],
  "asset_name_domain_keywords": ["Acme"],
  "platform_limits": { "twitter": 50 },
  "cron": null
}
```
- `name_keywords` — individual people to protect (executives).
- `domain_keywords` — brand/domain name variants to search for. Match
  confidence (`name_score`, and everything derived from it) is scored
  purely against these keywords — there's no separate handle/username
  lookup in the system.
- `platform_limits` — optional per-platform cap on how many results a
  sweep returns; omit or `0` = uncapped.
- `cron` — optional; set this to also put the client on an automatic
  recurring sweep. Leave `null` if you're only ever triggering discovery
  yourself via the API.

**Response** — the stored client record (same shape, plus `created_at`,
`last_run_at`, `last_run_status`).

Other client endpoints: `GET /clients` (list all), `GET /clients/{id}`,
`DELETE /clients/{id}` (also cascades: deletes this client's profiles and
published incidents).

---

### 3.2 Start discovery — `POST /discovery`

Searches every platform with a ready session (or one specific platform) for
this client's keywords, and saves whatever it finds as candidate profiles
(`status: pending`). Returns immediately — this does not wait for the
sweep to finish.

**Request**
```json
{
  "client_id": "acme-corp",
  "keywords": ["Acme Corp", "AcmeOfficial"],
  "platform": null,
  "tabs": ["people", "pages"],
  "callback_url": "https://your-service/callbacks/bi-jobs"
}
```
- `platform` — omit/`null` to sweep every ready platform; set to one of
  `facebook`, `twitter`, `instagram`, `youtube`, `telegram` to scope it.
- `keywords` — required unless you're re-resolving specific already-found
  profiles via `profile_ids` instead (see the DTO for that path).
- `callback_url` — optional; see §4 for what this does and its constraints.

**Response** — `202 Accepted`
```json
{ "job_id": "a1b2c3d4e5f6", "status": "queued" }
```

Track it via `GET /jobs/{job_id}` (§6). When the job reaches `done`, new
candidate profiles are queryable via `GET /profiles?client_id=acme-corp`.

---

### 3.3 Review and decide on candidates — `GET /profiles`, `PATCH /profiles/{id}`

**`GET /profiles?client_id=acme-corp&phase=discovery&status=pending`**

Returns the lightweight "card" shape — enough to decide approve/reject,
not the full scraped record:
```json
{
  "items": [
    {
      "id": "665f1a...",
      "platform": "twitter",
      "url": "https://x.com/acme_0fficial",
      "profile_name": "Acme Corp",
      "profile_image_url": "https://pbs.twimg.com/...",
      "status": "pending",
      "phase": "discovery",
      "name_score": 92,
      "followers": 1200,
      "entity_type": "",
      "keywords": ["Acme Corp"]
    }
  ],
  "total": 1,
  "counts": { "pending": 1, "approved": 0, "rejected": 0 },
  "limit": 100,
  "offset": 0
}
```
Useful query params: `status` (`pending`/`approved`/`rejected`), `platform`,
`priority` (`High`/`Medium`/`Low`), `match_level` (`high`/`medium`/`low`),
`search`, `limit`/`offset` for paging. All filtering happens server-side.

**`PATCH /profiles/{id}`** — the actual triage decision:
```json
{ "status": "approved" }
```
Approving auto-queues an analysis job for that profile's platform — you
don't call `POST /analysis` yourself for the normal path. Setting
`status: "rejected"` just marks it and stops there.

For approving many at once: `POST /profiles/bulk-patch` with
`{"profile_ids": [...], "status": "approved"}` — queues at most one
analysis job per (client, platform) pair touched, not one per profile.

If you already have a specific profile URL in hand (a tip, not something
discovery found): `POST /profiles/add-urls` with
`{"client_id": "...", "urls": ["https://..."]}` — adds it pre-approved and
queues analysis directly.

---

### 3.4 Analysis — usually automatic, `POST /analysis` for manual/catch-up

You generally never call this directly — approving a profile already
queues it. This endpoint exists for a manual "run analysis again" or a
catch-up sweep over everything approved-but-not-yet-analysed:
```json
{ "client_id": "acme-corp", "platform": null, "force": false }
```
`force: true` re-analyses every approved profile again, even ones already
scored — use only for an explicit re-run, not routine polling.

**Response** — same `202` / `{job_id, status}` shape as discovery.

---

### 3.5 Read the scored result — `GET /profiles?phase=analysis`

Once an analysis job is `done`, the same profile now carries the full
scraped-and-scored record:
```json
{
  "items": [
    {
      "id": "665f1a...",
      "client_id": "acme-corp",
      "client_name": "Acme Corp",
      "platform": "twitter",
      "url": "https://x.com/acme_0fficial",
      "username": "acme_0fficial",
      "profile_name": "Acme Corp",
      "followers": 1200,
      "location": "New York, NY",
      "last_post_date": "2026-07-30T00:00:00+00:00",
      "is_active": true,
      "status": "approved",
      "phase": "analysis",
      "risk_score": 84,
      "priority": "High",
      "published": false,
      "publish_hold_until": "2026-08-11T10:15:00+00:00",
      "screenshot_url": "/profiles/665f1a.../screenshot",
      "analysis_status": "success",
      "analysed_at": "2026-08-11T10:05:00+00:00",
      "logo_match": true,
      "username_match": true,
      "incident": { "...": "see §5 — this is a live preview of the finding" }
    }
  ],
  "total": 1, "counts": {}, "limit": 100, "offset": 0
}
```
`risk_score` (0–100) / `priority` are this engine's own internal triage
scoring — different from the `riskRating` (2–9) inside `incident`, which
is a separate, simpler scale defined for the published-finding record
(see §5). Don't conflate the two.

---

### 3.6 Publish the finding — `POST /profiles/{id}/publish`

This is the moment a result actually becomes a client-facing finding —
nothing is written to the durable findings store before this (or before
`publish_hold_until` passes and it auto-publishes; see §5). Also available
in bulk: `POST /profiles/publish-all` with
`{"client_id": "...", "platform": null, "mode": "all"}` (`mode` can scope
to `"recent"` = last 24h, `"2days"`, or `"week"`).

**Response** — the same full profile shape as §3.5, now with
`published: true`.

---

### 3.7 Read confirmed findings — `GET /published-incidents`

The durable, client-facing output of the whole pipeline — what §3.6 just
wrote. See §5 for the full field reference and an example.
```
GET /published-incidents?client_id=acme-corp&platform=twitter&limit=50&offset=0
```

## 4. Async pattern: jobs, polling, and webhooks

`POST /discovery` and `POST /analysis` both return `202` with a `job_id`
immediately. Two ways to know when the work is done:

**Poll** — `GET /jobs/{job_id}`:
```json
{
  "id": "a1b2c3d4e5f6",
  "kind": "discovery",
  "client_id": "acme-corp",
  "status": "running",
  "found": 34,
  "total": 50,
  "new_profiles": 12,
  "error": "",
  "started": "2026-08-11T10:00:00+00:00",
  "finished": "",
  "platforms": {
    "twitter": { "status": "running", "processed": 20, "total": 50, "eta_seconds": 90 }
  },
  "blocked_by": null
}
```
`status` is one of `queued` / `running` / `done` / `failed` / `cancelled`.
`blocked_by` tells you if this job is queued behind another one holding
the same platform's session lock — useful for surfacing "why is this
taking a while" rather than a caller guessing. For incremental progress
without re-fetching the whole job, `GET /jobs/{id}/events?after_seq=N`
returns only events newer than `N`.

**Webhook** — pass `callback_url` at job creation; on completion the
engine `POST`s the same job payload shown above to that URL, once, with
retries. If `webhook_secret` is configured on this engine, the request
carries `X-BI-Signature: sha256=<hmac>` (HMAC-SHA256 over the raw body) —
verify it if you want to trust the callback came from here and wasn't
guessed by something else.

**Important if your callback endpoint is on a private/internal
address**: the engine refuses to deliver a callback to any URL that
resolves to a private, loopback, or link-local IP (SSRF hardening — see
`services/webhook_service.py`). If your service isn't on a publicly
resolvable address, `callback_url` won't work and you should poll instead.
This is worth confirming with whoever operates this engine before you build
against the webhook path.

## 5. The finding/output data shape (`incident`)

This is the record that actually answers "did we find an impersonator."
It's nested as the `incident` field on a `phase=analysis` profile (§3.5),
and it's exactly what gets written to the durable findings store on
publish:

```json
{
  "title": "Similar Twitter Account Acme Corp Found",
  "category": "Brand Infringement",
  "subCategory": "socialhandlers",
  "assetType": "Twitter",
  "source": "https://x.com/acme_0fficial",
  "date": "2026-08-11T10:05:00+00:00",
  "description": "Name: Acme Corp Url: https://x.com/acme_0fficial",
  "riskRating": "7",
  "domain": "acme.com",
  "orgId": "acme-corp",
  "assetCategory": "Twitter",
  "assetName": "Acme",
  "thirdParty": false,
  "socialProfileInfo": {
    "isActive": true,
    "isSimilarName": true,
    "isSimilarLogo": true,
    "numberOfFollowers": 1200,
    "profileName": "Acme Corp",
    "location": "New York, NY",
    "profileImage": "https://pbs.twimg.com/...",
    "lastPostDate": "2026-07-30T00:00:00+00:00",
    "posts": null
  },
  "evidence": {
    "screenshot": true,
    "fieldsRead": 5,
    "analysisStatus": "success"
  }
}
```
- `category`/`subCategory` — `("impersonation", "ExecutivePeople")` when
  the match came from a person's name keyword, `("Brand Infringement",
  "socialhandlers")` when it came from a brand/domain keyword.
- `riskRating` — `"2"`–`"9"` (string), a simpler, separate scale from the
  profile's own `risk_score` (see §3.5's note).
- `orgId` — your `client_id`, unchanged. This is the field to filter on if
  you're storing these downstream keyed by client.
- Any `null` in `socialProfileInfo` means "we don't know," not "false" —
  e.g. `isActive: null` means no last-post date was ever found, which is a
  different claim than "confirmed dormant." Treat `null` as "unknown," not
  as falsy.

**`GET /published-incidents?client_id=acme-corp`** — the direct way to
read this feed, added specifically so you don't have to derive it from
`GET /profiles`:
```json
{
  "items": [ { "...": "one incident object, exactly the shape above, plus \"id\"" } ],
  "total": 1,
  "limit": 50,
  "offset": 0
}
```
Optional `platform` param scopes it to one platform id (`facebook`,
`twitter`, `instagram`, `youtube`, `telegram`); `limit`/`offset` page
through results, most recently updated first. This only ever returns
records that were actually published — nothing appears here before
`POST /profiles/{id}/publish` (or auto-publish) has run.

## 6. Jobs API reference

| Method & path | Purpose |
|---|---|
| `GET /jobs?client_id=&limit=` | recent jobs, optionally scoped to one client |
| `GET /jobs/{id}` | current status of one job (§4) |
| `GET /jobs/{id}/events?after_seq=` | incremental progress events since `after_seq` |
| `POST /jobs/{id}/cancel` | cancel a queued/running job |

## 7. Supporting endpoints (not part of a normal integration)

These exist for the operator running this engine (session setup, mail
alerts, the scheduler, dashboards) — you generally won't call them from an
external platform integration, but they're listed for completeness:

- `GET /health/live`, `/health/ready`, `/health/platforms`, `/metrics` —
  liveness/readiness probes and a Prometheus scrape target.
- `GET /incidents` — **not** the findings feed from §5. This is an
  unrelated operational log of job *failures* (a session got checkpointed,
  a quota ran out) with a 14-day TTL, meant for whoever operates the
  scrapers, not for downstream business consumption.
- `/sessions/*` — logging platform accounts in (cookies/API keys), used to
  keep the scraper pool alive. Not something a calling platform manages.
  `/settings/*`, `/scheduler/*` — mail alert config and the cron
  scheduler; operator-only.

## 8. Platform ids

Use these exact strings anywhere a `platform` field is accepted:

| id | Name | Notes |
|---|---|---|
| `facebook` | Facebook | discovery + analysis |
| `twitter` | X / Twitter | discovery + analysis |
| `instagram` | Instagram | discovery + analysis |
| `youtube` | YouTube | API-key based, no browser session lock contention with other jobs |
| `telegram` | Telegram | discovery + analysis |

A platform can be temporarily unavailable if its session isn't logged in —
check `GET /health/platforms` for live per-platform readiness before
assuming a sweep will actually cover it.

## 9. Quick integration checklist

1. Confirm network reachability is trusted (no auth layer — §1).
2. Decide poll vs. webhook (§4) — webhook only works if your endpoint has
   a publicly resolvable address.
3. `POST /clients` once per brand you're protecting.
4. `POST /discovery` → poll/webhook → `GET /profiles?phase=discovery`.
5. Decide your approve/reject logic against `PATCH /profiles/{id}` (or
   have a human do it in the bundled UI — both write to the same data).
6. Poll/webhook the auto-queued analysis job → `GET
   /profiles?phase=analysis` for scored results.
7. `POST /profiles/{id}/publish` (or `publish-all`) when you're ready to
   treat a result as a confirmed finding.
8. Pull confirmed findings via `GET /published-incidents?client_id=...`
   (§5) — the durable, publish-only feed, not the live preview embedded
   in `GET /profiles`.
